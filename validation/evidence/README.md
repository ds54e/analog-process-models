# Validation evidence

This directory contains compact committed summaries for implementation
milestones and release claims. It is not a dump of raw simulator output.
Detailed reproducible netlists, raw data, logs, and full reports remain under
ignored `.apm/results/` paths and are regenerated by release validation.

Historical `m0-*.md` through `m10-*.md` files document v1.0.0 only. They do
not satisfy a v2 or v3 gate. Historical v2 release evidence uses a `v2_`
prefix.

Post-v2 development milestones use a `v3_` prefix. The frozen V3-N0/V3-N1/V3-N2
noise summaries establish the stated real-tool characterization, method, and
catalog/comparison capability behind released v3.0.0. They are development
history rather than standalone release attestations and do not amend immutable
v1/v2 evidence. The summaries are
`v3_n0_noise_spike.json`, `v3_n1_noise_method.json`, and
`v3_n2_noise_catalog.json`.

V3-N3 exact-candidate evidence is `v3_release_candidate.json`. The annotated
tag now exists at that exact candidate. Exact-tag post-release evidence is
`v3_post_release_requalification.json`; it records the independent fresh-clone
18/18 result before the GitHub Release was created. Post-v3 public-readiness
maintenance is recorded separately in `public_readiness_v3.json`. That file's
PRIVATE observations remain the historical pre-publication audit. The later
controlled publication, `main` protection, and GitHub security-feature state
are recorded in `publication_v3.json` without rewriting the earlier evidence.

## Status vocabulary

- `validated`: the required real environment/tool/test ran and directly
  supports the stated claim.
- `structurally_checked`: deterministic syntax/structure/static checks ran,
  but the real backend did not.
- `experimental_unverified`: the artifact is intentionally supplied without
  real-backend validation, as allowed for model-only Spectre.
- `blocked`: a required validation could not complete; this is not a pass.

Missing evidence is never a pass.

## Compact evidence fields

Each summary should identify, where applicable:

```text
Gate / milestone
Status and date
Git/source state
Reference environment and tool versions
Commands and exit codes
Observed properties
Input/output/report hashes
Explicit limitations
```

Do not paste large logs. Hash-link the relevant full generated report and
summarize property checks.

## Real-tool evidence

Model/compiler evidence distinguishes:

1. licensed source present;
2. compilation completed;
3. ngspice loaded the generated OSDI;
4. a real device simulation completed; and
5. terminal/property checks passed.

A file existing on disk or a structural parse is not real-tool execution.

## Statistical evidence

Benchmark and native variation evidence covers cohorts rather than a single
draw. Relevant checks include:

- same-seed replay and different-seed difference;
- centered normalized means and nonzero spread;
- intended Global/model-global sharing;
- intended Local/mismatch independence;
- `1/sqrt(match_size)` or upstream area scaling; and
- combined Benchmark All semantics where defined.

Benchmark Global/Local/All and upstream process/mismatch identities remain
separate in every summary.

## Model-behavior evidence

APM-authored family evidence binds to documented observable contracts:
multi-VT Vth/Ion/Ioff ordering, short-channel/length trends, positive finite
terminal metrics, APM016F NFIN scaling, and independently selected parameter
generation. Simulator convergence alone is insufficient.

## Licensing evidence

The provenance audit identifies every shipped third-party asset by upstream
URL/revision/path, applicable terms, retained notices, exact hash, and
modification status. Repository-root licensing is not used as a substitute for
file-level review.

## Spectre evidence

Without a real Spectre installation, evidence remains
`structurally_checked` with backend status `experimental_unverified`.
Static audits cover every family binding, public name, benchmark
Global/Local/All structure, deterministic generation, and prohibited Virtuoso
scope. They do not establish parse validity or numerical conformance.

## Released clean-clone evidence

The v3 candidate evidence was produced by `apm validate --release --output
DIR` from an exact-commit fresh clone after `tools/attest_clean_clone.py`. It
shows 18/18 required gates, nonempty existing evidence for each gate, and
status `pass`. The exact annotated tag was then independently requalified from
a second fresh HTTPS clone with the complete catalog executed from empty output
before strict all-reuse resume qualification. See
`docs/release-validation.md` for the current reproducibility path and the
historical tag-absence compatibility detail.
